En DevOps no hay magia fuera del repositorio. El código de la app, los pipelines, los manifiestos y Terraform son archivos. Si no controlas el cambio, no controlas la producción.

Conferencia

La caja negra

Git no es GitHub. Git es un motor local de instantáneas. GitHub, GitLab y similares son plazas públicas donde esas instantáneas se revisan, se discuten y se despliegan. Primero entiende el motor; después la plaza.

Cada commit es una foto del proyecto en un instante, con un autor, un mensaje y un padre. Una rama es solo un puntero móvil a un commit. Fusionar es hacer que dos historias vuelvan a ser una.

Abstracción CS50Trata Git como una máquina de tiempo con nombres. clone copia el universo. branch crea una línea de tiempo paralela. merge las reconcilia. pull request es el ritual social para no fusionar a ciegas.

Lo que debes saber hacer

  • Clonar, ver el estado, agregar, confirmar y enviar cambios.
  • Crear ramas con propósito: una idea, una rama.
  • Abrir una solicitud de cambio (pull request) y responder revisión.
  • Fusionar, rebasear con cuidado y resolver conflictos sin pánico.
  • Entender que la infraestructura también es código versionado.

Comandos que sí vas a usar

git clone <url>
git status
git add .
git commit -m "Explica el porqué, no el qué"
git switch -c feature/dns-ttl
git push -u origin HEAD
git log --oneline --graph

Ramas, fusión y pull requests

Una rama barata te permite experimentar. El pull request no es burocracia: es el momento en que otro cerebro lee tu cambio antes de que toque main. Ahí se discute correctitud, diseño y estilo — la misma rúbrica de este curso.

Fusionar (merge) conserva la historia de la rama. Rebasear reescribe para que parezca lineal. En equipos, prefiere merge o squash según la convención del repositorio; no improvises en main.

Errores comunes

  • Commits gigantes que mezclan formato, lógica y secretos.
  • Subir .env, llaves SSH o kubeconfig. Eso no se borra del historial con un commit nuevo.
  • Trabajar directo en main y luego pelear con todo el mundo.

Cortos

Un concepto por tarjeta. Léelos en voz alta si puedes.

Commit

Un commit es un objeto inmutable. Si cambias la historia, creas commits nuevos. Por eso force-push en ramas compartidas duele.

Rama

main, develop o trunk son convenciones, no magia. El servidor no sabe cuál es sagrada hasta que tú proteges la rama.

Pull request

Es una conversación con diff. El botón verde es un despliegue social: alguien apuesta a que esto no rompe producción.

Conflicto

Git te pide que elijas líneas. El conflicto no es un error de Git: es dos verdades sobre el mismo archivo.

Recorrido

Como el walkthrough de CS50: solo para arrancar, no para sustituir el problem set.

  1. Instala Git y configura user.name y user.email.
  2. Crea un repositorio vacío y haz tres commits pequeños con mensajes claros.
  3. Abre una rama, cambia un archivo, publícala y abre un pull request.
  4. Fusiona el PR y observa el grafo con git log --graph.

Problem set

Rúbrica: correctitud — El historial se puede leer de atrás hacia adelante. · diseño — Cada commit hace una sola cosa. · estilo — Mensajes en imperativo, sin ruido, sin secretos.
